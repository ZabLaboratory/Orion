## Finding and change

The allocation profile collected after the previous size-lowering optimization
still attributed 75.55% cumulative benchmark allocation to `adaptStaticNode`
(1.26 GB across the profile), including 303.57 MB under decoding child arrays
into maps and 231.19 MB in `json.RawMessage.UnmarshalJSON`. The compiler was
copying each nested property value into temporary maps before lowering it.

This candidate scans the already-validated layout into `RawMessage` views over
the owned layout buffer and visits child-array elements without first decoding
them into `[]map[string]json.RawMessage`. It preserves last-duplicate-wins
behavior, escaped/invalid UTF-8 property-key decoding, non-object child
tolerance, and the JSON decoder fallback. The returned compiled bundle remains
independent of the caller's original input bytes. This is generic compiler
behavior; it adds no product-specific branch and touches no Pulsar code.

## A/B compiler benchmark

Machine: Windows/amd64, AMD Ryzen 7 3800X. Fixture:
`BenchmarkCompileStaticLSMLRepresentative` (250 text nodes), against the same
merged #453 base tree.

Command on each revision:

```text
go test ./internal/compiler -run '^$' -bench '^BenchmarkCompileStaticLSMLRepresentative$' -benchmem -benchtime=2s -count=5
```

| Revision | Median time | Median B/op | Median allocs/op |
| --- | ---: | ---: | ---: |
| Base #453 | 3.866 ms | 1,095,138 | 13,345 |
| Candidate | 2.786 ms | 993,053 | 11,821 |

The candidate is 27.9% faster by median time, allocates 9.3% fewer bytes, and
uses 1,524 fewer allocations/op (11.4%). These are local compiler
microbenchmark results, not production latency claims.
