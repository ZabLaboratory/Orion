## Summary

Wires `internal/bluehost/host.go` to the async effect invocation/completion
protocol Blue PR #313 added to `runtime/go` (`StepResult.Invocations` +
`Runtime.Complete`, `blue.effect.invocation.v1` / `blue.effect.completion.v1`).
`core.http.request` invocations a `core.effect.invoke@1` node emits are now
executed as real outbound HTTP calls (through the existing fail-closed
`effects.EgressPolicy`), off the `Step` goroutine via the shared
`effects.Runner` worker pool, and reported back through `Runtime.Complete`
so the program's own `on-event` node observes the completion on a later
`Step`. `db.query`/`source.read` stay out of scope, as scoped.

Dependency note: Orion's `go.mod` was pinned to
`Blue/runtime/go@96b3dcb4c841`, a commit that predates the async protocol
entirely (`StepResult` had no `Invocations` field, no `Runtime.Complete`
method at all). Bumped to `e96bc5709899` (the commit the work item named)
to pick it up — this was a real blocker, not a style choice.

Architecture note (documented rather than improvised, per the work item):
`blueruntime`'s canonical-digest functions (`digestValue`/`canonicalBytes`)
are unexported, so a host package cannot compute a
`blue.effect.completion.v1`'s `response_digest`/`completion_digest` using
Blue's own code. `internal/providers/canonical.go` already carries a
byte-identical reimplementation of the same LSML canonicalization
algorithm for the same reason (event digests). Extracted that
implementation into a new leaf package, `internal/canonical`, so
`internal/bluehost` can depend on it too — `internal/providers` already
imports `internal/bluehost` (`events.go`'s `InjectActive`), so `bluehost`
importing `providers` directly would be a cycle. `internal/providers`
keeps `CanonicalBytes`/`Digest` as thin re-exports; no caller-visible
change there.

`internal/providers/policy.go`'s `httpRequestProvider()` descriptor
already declared `operation: "request"`/`preview: "noop"` — matches the
bluespike fixture's `requires` entry exactly, so provider admission needed
no changes.

## Écarts / hypothèses

- The HTTP effect's response shape (`{status, body, headers}`) mirrors the
  legacy `internal/runtime/exec_effects.go` convention for consistency —
  not specified anywhere in the async ABI itself (the capability's
  `response_type` is opaque `core.json`).
- `httpEffectTimeout` reads the request's `timeout_ms` field (the
  `core.http.request` seed convention); `invocation["deadline_at_ms"]` is
  NOT used for the host-side network timeout — `Runtime`'s clock is fixed
  at `0` (`NewRuntime`'s `clock: func() int64 { return 0 }`), so
  `deadline_at_ms` is deterministic-core bookkeeping, not a real wall-clock
  deadline a host can schedule against.
- No explicit `Stop()`/shutdown wiring for the new `effects.Runner`
  started in `wireSceneIntent` — this stateless-cutover surface (#331) has
  no graceful-shutdown hook of its own yet; the pool's goroutines are
  reclaimed on process exit, same posture as the rest of this dark-by-default
  surface.
