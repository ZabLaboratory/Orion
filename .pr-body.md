## Summary

`internal/api/scene_intent.go:243,250` called `bluehost.Host.Prepare/Take`
with `providers=nil, policy=nil` unconditionally. `checkProviders`
(`blue-runtime-go`) refuses any program declaring `requires` with
`CAPABILITY_UNAVAILABLE` unless a matching, correctly-shaped
`blue.capability-provider.v1` descriptor is present — so every
capability-requiring program failed closed through `POST
/api/v1/host/scene-intent`, regardless of what ZabCanvas resolved. A
display-only program (no `requires`) was unaffected, which is why this
went unnoticed through #331's own proof.

- `internal/providers` — Orion's Zab capability-provider catalogue
  (`Registry()`): `core.http.request`, `show.emit`, `overlay-app` (the
  stateless-cutover successors of the effects previously implemented
  directly in Orion, per ADR-BLUE-012 §4.3/§6.6). Each descriptor
  round-trips through the real `blueruntime.ParseProvider`.
- `internal/providers.Policy(httpEgressAllowed)` — the host-side
  `CapabilityPolicy` admission gate. `checkProviders` only ever calls it
  with `(requirement, provider, mode)`, never the per-call request payload,
  so this is the coarsest decision available: whether `core.http.request`
  admits at all for this deployment, mirrored from
  `internal/effects.EgressPolicy`'s existing deny-by-empty-allowlist
  posture. Per-request host vetting still happens in the effect executor
  at dispatch time.
- `internal/providers.BuildEvent`/`InjectActive` — the active-only
  successor of the legacy stream-rule routing (§4.3 puce 4): builds a
  valid `blue.runtime.event.v1` envelope from a Zab-canonical event
  (payload/event digests computed via a local reimplementation of
  blueruntime's private LSML canonicalization — it isn't exported) and
  routes it exclusively to the on-air `bluehost` slot. Library-only in
  this PR: no live Quasar transport exists yet against the stateless
  `bluehost` path to attach it to, so wiring a real event source is out
  of scope here.
- `SceneIntentDeps` grows `Providers []map[string]any` and `Policy
  blueruntime.CapabilityPolicy` (both nil-safe). `cmd/orion/scene_intent_wiring.go`
  wires them from `providers.Registry()`/`providers.Policy(...)`, gated on
  `cfg.HTTPEgressAllowHosts` the same way the legacy `http.request`
  executor was.

## Écarts / hypothèses

- **Capability naming is my own design, not Blue's.** No Blue compiler
  emits `requires`/`effects` for these capabilities yet (checked: no
  fixture, no test, ADR-BLUE-012 references #135/#155/#158/#283 as still
  open/`TRANSFER_TO_OWNER_REPO`/`REUSE_AS_GATE_B_WORK`). I picked
  `core.http.request`/`show.emit`/`overlay-app` as capability identifiers
  matching the platform's existing opcode-naming convention
  (`core.http.request@1`, `core.show.emit@1` from ADR 009/010) minus the
  `@version` suffix (the provider schema's `capability` field uses a
  simpler identifier pattern that doesn't allow `@`). If/when Blue's
  compiler starts emitting real `requires` for these effects, the
  capability/version/operation/request_type/response_type tuple here MUST
  match exactly or `effectTypesMatch` will refuse admission even with a
  present, healthy provider — flagging this explicitly since it's a
  cross-repo contract with no test enforcing it yet (Conduit/Blue owns
  confirming or correcting the naming).
- **Zab event injection adapter is a library, not a wired transport.** I
  built `BuildEvent`/`InjectActive` (tested) but did not invent an HTTP/WS
  consumer to drive it — no such transport exists against `bluehost` yet,
  and building one felt like scope creep past "providers, policies,
  routage active-only" into a new network surface. Flagging as an open
  follow-up rather than silently deciding it was in scope.
- `internal/effects/dbquery.go`/`dbschema.go`, `internal/runtime/*stream_rule*`,
  and Canvas durability (#154/#287) are untouched per the bail's explicit
  exclusions.
